The Helm chart provides a `values.yaml` that maps to the operator's command-line flags and Kubernetes resource configuration.

## Default values

```yaml
replicaCount: 1

image:
  repository: ghcr.io/dorgu-ai/dorgu-operator
  tag: ""  # Defaults to chart appVersion
  pullPolicy: IfNotPresent

validation:
  requeueInterval: 60s

leaderElection:
  enabled: true

operator:
  autoCreateClusterPersona: true
  clusterPersonaEnsureInterval: ""

metrics:
  enabled: true
  bindAddress: ":8443"
  secure: true

healthProbe:
  bindAddress: ":8081"

argocd:
  enabled: true

prometheus:
  enabled: false
  url: ""

websocket:
  enabled: false
  port: 9090
  service:
    type: ClusterIP
    port: 9090

healthCheck:
  enabled: true
  interval: 60s

safety:
  excludedNamespaces: []

metricsServer:
  enabled: true

dorguEvents:
  retention: 24h
  maxRecords: 2000

llm:
  provider: ""
  model: ""
  existingSecret: ""
  existingSecretKey: "ANTHROPIC_API_KEY"
  apiKey: ""
  createSecret: false

aiRemediation:
  enabled: false

resources:
  limits:
    cpu: 500m
    memory: 128Mi
  requests:
    cpu: 10m
    memory: 64Mi

serviceAccount:
  create: true
  name: ""
  annotations: {}

nodeSelector: {}
tolerations: []
affinity: {}
```

## Value reference

### Image

| Value | Type | Default | Description |
|-------|------|---------|-------------|
| `image.repository` | string | `ghcr.io/dorgu-ai/dorgu-operator` | Container image repository |
| `image.tag` | string | Chart `appVersion` | Image tag override |
| `image.pullPolicy` | string | `IfNotPresent` | Image pull policy |
| `imagePullSecrets` | array | `[]` | Image pull secrets for private registries |

### Replicas and scheduling

| Value | Type | Default | Description |
|-------|------|---------|-------------|
| `replicaCount` | int | `1` | Number of operator replicas |
| `leaderElection.enabled` | bool | `true` | Enable leader election (required for replicas > 1) |
| `nodeSelector` | object | `{}` | Node selector for pod scheduling |
| `tolerations` | array | `[]` | Pod tolerations |
| `affinity` | object | `{}` | Pod affinity rules |

### Removed: the validating webhook

Chart 0.12.0 removed the Deployment validating admission webhook, its `webhook.enabled`, `webhook.mode` and `webhook.port` values, its Service, and its `ValidatingWebhookConfiguration`. It never produced a warning or a denial in any release, so removing it changes no admission behaviour on your cluster.

<Warning>
  **An install or upgrade that still sets `webhook.enabled=true` fails** with a message saying the webhook was removed, rather than silently dropping the value. Remove `webhook.*` from your values files before upgrading to 0.12.0. If you run the binary directly, the `--enable-webhook`, `--webhook-mode`, `--webhook-cert-path`, `--webhook-cert-name` and `--webhook-cert-key` flags are gone too, and passing one stops the operator from starting.
</Warning>

Persona validation itself is unaffected: the controller still validates every Deployment against its persona and records the result on the persona's status. See [validation](/operator/features/validation).

### Self-healing

| Value | Type | Default | Description |
|-------|------|---------|-------------|
| `healthCheck.enabled` | bool | `true` | Enable the health-check reconciler: detection, diagnosis, and remediation proposals. **On by default since chart 0.8.0**, and in the operator binary itself since 0.12.0. Set it to `false` to run without self-healing. |
| `healthCheck.interval` | duration | `60s` | How often the reconciler runs a detection cycle |
| `metricsServer.enabled` | bool | `true` | Enable metrics-server integration for container-level CPU/memory detection |

Rendered as `--enable-health-check=<value>` on the operator container either way, so the setting is always visible in the pod spec:

```bash
kubectl -n dorgu-system get deploy dorgu-operator \
  -o jsonpath='{.spec.template.spec.containers[0].args}{"\n"}'
```

When `healthCheck.enabled` is `false`, the operator still validates personas, records their health, and discovers the cluster, and from chart 0.12.0 it never opens an incident or proposes a fix. Chart 0.11.x and older did not fully honour this: an older code path still opened `OOMKilled` incidents and wrote `RemediationAction` proposals with detection off, without the guardrails the health-check path applies. Setting `metricsServer.enabled=false` passes `--enable-metrics-server=false`; OOM and crash-loop detection read pod status and are unaffected, but usage and saturation signals go dark. See [Self-healing](/operator/features/self-healing).

<Warning>
  **Upgrading from a chart older than 0.8.0 turns detection on.** A release that never set `healthCheck.enabled` will start detecting after the upgrade: expect `IncidentMemory` records to appear, and `RemediationAction` proposals wherever the ClusterPersona self-healing mode is `propose` (the default). Nothing is applied without approval. To keep the old behaviour, upgrade with `--set healthCheck.enabled=false`.
</Warning>

### Remediation safety

| Value | Type | Default | Description |
|-------|------|---------|-------------|
| `safety.excludedNamespaces` | array | `[]` | Extra namespaces Dorgu never proposes a remediation in. Maps to `--safety-excluded-namespaces`. **New in chart 0.12.0.** |

Dorgu never proposes a remediation for a persona in a protected namespace. Three sources make up the list:

- **`kube-system`**, always.
- **The namespace the operator runs in**, always. The chart sets `POD_NAMESPACE` on the operator container from the downward API, so with the documented install that is `dorgu-system`, and with any other `--namespace` it is that one.
- **Anything you add**, through `safety.excludedNamespaces` here or through `spec.policies.selfHealing.excludeNamespaces` on the [ClusterPersona](/cli/architecture/crds#self-healing-policy). Both are honoured.

```yaml
safety:
  excludedNamespaces:
    - payments
    - ingress-nginx
```

Detection is not affected. An incident in a protected namespace is still recorded as an `IncidentMemory` with its diagnosis; the operator just proposes no fix for it.

<Note>
  **Fixed in operator v0.12.0.** Older releases protected a hardcoded `dorgu-operator-system`, the kustomize default, rather than the namespace the chart actually installs into. With the documented `--namespace dorgu-system` install, Dorgu's own namespace was not protected at all. Upgrade if you run 0.11.x.
</Note>

### DorguEvent retention

| Value | Type | Default | Description |
|-------|------|---------|-------------|
| `dorguEvents.retention` | duration | `24h` | How long a `DorguEvent` record is kept before the cleaner removes it. Maps to `--dorgu-event-retention`. |
| `dorguEvents.maxRecords` | int | `2000` | Maximum records kept regardless of age; the oldest go first. `0` drops the cap and leaves retention as the only bound. Maps to `--dorgu-event-max-records`. |

`DorguEvent` records are Dorgu's own log of what it saw, readable with `kubectl get dorguevent -A`. They live in etcd, so they are bounded twice over: by age, and by count.

The count bound is the one that holds on a large cluster. Records arrive in proportion to cluster size, so a time window alone bounds nothing: a five-app clean-room cluster produced 187 records in 100 minutes, roughly 2,700 a day, every one of them inside the 24-hour window and all of them in etcd. The cleaner runs every 30 minutes, deletes oldest-first, and runs one pass at startup rather than waiting a full interval, because a restarted operator inherits the largest backlog it will ever see.

Both flags are rendered on the operator container unconditionally, so the pod spec always states what bounds the record count, `maxRecords: 0` included:

```bash
kubectl -n dorgu-system get deploy dorgu-operator \
  -o jsonpath='{.spec.template.spec.containers[0].args}{"\n"}'
```

<Note>
  **New in operator v0.10.0.** Before it, the cleaner had no `delete` permission on `dorguevents.dorgu.io` at all: it ran every cycle, failed, and removed nothing. The ClusterRole now grants `delete` on Dorgu's own CRD and on no workload kind. See [why that verb is there](/security-and-permissions#why-the-operator-can-delete-dorguevents).
</Note>

### AI

| Value | Type | Default | Description |
|-------|------|---------|-------------|
| `llm.provider` | string | `""` | `claude` enables Anthropic. Empty disables AI. `gemini` enables AI *diagnosis* only, since the remediation planner requires `claude`. |
| `llm.model` | string | `""` | Model override. Empty uses the provider default (`claude-sonnet-4-6` for the planner). |
| `llm.existingSecret` | string | `""` | Name of a pre-created Secret holding the API key. **Preferred.** |
| `llm.existingSecretKey` | string | `ANTHROPIC_API_KEY` | Key within that Secret |
| `llm.apiKey` | string | `""` | Dev only. A raw key, requires `createSecret=true` |
| `llm.createSecret` | bool | `false` | When true and `apiKey` is set, the chart creates the Secret |
| `aiRemediation.enabled` | bool | `false` | Maps to `--enable-ai-remediation`. Only takes effect when `llm.provider` is set. **`false` is also the current recommendation**, not just the default: see [why AI is off](/operator/configuration/ai-setup#why-it-is-off-and-what-that-costs-you). |

Both AI values default off, so a chart installed with no `--set` flags makes no API calls and spends nothing. Rules run either way.

The key is always delivered to the pod as an environment variable via `secretKeyRef` (`ANTHROPIC_API_KEY` for `claude`), and the chart never passes it as a container argument.

</Warning>

### Bootstrap

| Value | Type | Default | Description |
|-------|------|---------|-------------|
| `operator.autoCreateClusterPersona` | bool | `true` | Auto-create a ClusterPersona named `dorgu-cluster` on startup if none exists |
| `operator.clusterPersonaEnsureInterval` | duration | `""` (operator default `2m`) | How often the operator re-ensures that persona exists. Clamped to a 30s minimum. Only applies when `autoCreateClusterPersona` is `true`. |

Set `autoCreateClusterPersona: false` if you manage ClusterPersonas through GitOps and do not want the operator creating one.

### Validation

| Value | Type | Default | Description |
|-------|------|---------|-------------|
| `validation.requeueInterval` | duration | `60s` | How often the ApplicationPersona controller re-validates |

### Metrics and probes

| Value | Type | Default | Description |
|-------|------|---------|-------------|
| `metrics.enabled` | bool | `true` | Enable metrics endpoint |
| `metrics.bindAddress` | string | `:8443` | Metrics server bind address |
| `metrics.secure` | bool | `true` | Serve metrics over HTTPS with authentication |
| `healthProbe.bindAddress` | string | `:8081` | Health and readiness probe bind address |

### ArgoCD

| Value | Type | Default | Description |
|-------|------|---------|-------------|
| `argocd.enabled` | bool | `true` | Enable ArgoCD Application watching |

The watcher auto-detects whether the ArgoCD CRD exists. If `enabled: true` but the CRD is absent, the watcher silently skips.

### Prometheus

| Value | Type | Default | Description |
|-------|------|---------|-------------|
| `prometheus.enabled` | bool | `false` | Enable Prometheus baseline learning |
| `prometheus.url` | string | `""` | Prometheus server URL |

Example: `http://prometheus-server.monitoring:9090`

### WebSocket

| Value | Type | Default | Description |
|-------|------|---------|-------------|
| `websocket.enabled` | bool | `false` | Enable the operator's WebSocket server |
| `websocket.port` | int | `9090` | WebSocket server port |
| `websocket.service.type` | string | `ClusterIP` | Service type for the WebSocket endpoint |
| `websocket.service.port` | int | `9090` | Service port |

When enabled, the chart creates a Service on the specified port. No Dorgu CLI command connects to it since CLI `v0.13.0`, so leave it off unless you have your own client. See [WebSocket server](/operator/features/websocket).

| Value | Type | Default | Description |

## Example: the recommended default

Nothing to set. Detection, rule-based diagnosis, and rule-based remediation are all on, and no key is involved:

```bash
helm install dorgu-operator oci://ghcr.io/dorgu-ai/dorgu-operator-charts/dorgu-operator \
  --namespace dorgu-system --create-namespace
```

## Example: opting in to AI

Create the Secret out of band, then:

```yaml
# healthCheck.enabled and metricsServer.enabled are already true by default.
healthCheck:
  interval: 30s

llm:
  provider: claude
  existingSecret: dorgu-llm
  existingSecretKey: ANTHROPIC_API_KEY

# Leave this false for AI root-cause prose with rule-written plans, which is
# the recommended shape. Setting it true hands the plan to the model, and
# needs operator v0.11.0 or newer to produce one that can be applied.
aiRemediation:
  enabled: false
```

## Example: Production deployment

```yaml
replicaCount: 2

healthCheck:
  enabled: true
  interval: 30s

leaderElection:
  enabled: true

safety:
  excludedNamespaces:
    - payments

argocd:
  enabled: true

prometheus:
  enabled: true
  url: "http://prometheus-server.monitoring:9090"

resources:
  limits:
    cpu: "1"
    memory: 256Mi
  requests:
    cpu: 100m
    memory: 128Mi

affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchExpressions:
              - key: app.kubernetes.io/name
                operator: In
                values:
                  - dorgu-operator
          topologyKey: kubernetes.io/hostname
```
