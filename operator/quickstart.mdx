This guide installs the Dorgu Operator with the self-healing loop and AI planning enabled, then walks a real incident from detection to healed.

## Step 1: Install the operator

The self-healing loop is **on by default** as of chart 0.8.0. AI is the part you opt into.

```bash
kubectl create namespace dorgu-system

# Optional — enables AI diagnosis and AI-written remediation plans
kubectl create secret generic dorgu-llm -n dorgu-system \
  --from-literal=ANTHROPIC_API_KEY=sk-ant-...
```

Then install the operator:

<OperatorInstallAI />

Omitting `--version` resolves the newest published chart. To pin an exact chart version, see the [installation guide](/operator/installation). Drop the `llm` and `aiRemediation` flags to run rule-based: detection, diagnosis, and remediation all work without a key. `healthCheck.interval=30s` only tightens the loop for the demo; the default is 60s. Metrics-server integration is on by default and adds container-level usage signals.

<Note>
  To install the operator without the detection loop, add `--set healthCheck.enabled=false`. It will still validate personas and discover the cluster, but it will never open an incident or propose a fix.
</Note>

```bash
kubectl wait --for=condition=ready pod -l app.kubernetes.io/name=dorgu-operator \
  -n dorgu-system --timeout=120s
```

Confirm the loop and the planner started:

```bash
kubectl -n dorgu-system logs deploy/dorgu-operator | grep -i "AI \|health check"
```

Look for `AI diagnosis enabled` and `AI remediation planning enabled`. See [AI setup](/operator/configuration/ai-setup) if either is missing.

## Step 2: Confirm cluster discovery

The operator auto-creates a cluster-scoped `ClusterPersona` named `dorgu-cluster` on startup and populates it with nodes, add-ons, capacity, Kubernetes version, and platform type — typically within seconds.

```bash
dorgu cluster status
dorgu health
```

`dorgu health` should report your nodes `Ready`, resource saturation, control-plane health, and `Active Incidents: 0`.

<Note>
  On a managed cluster (EKS, GKE, AKS) the control plane is not visible as pods, so it is reported as `Healthy (external/managed)`. That is expected.
</Note>

If the cluster already runs applications, `dorgu health` also prints an `Unmonitored` section naming the Deployments no persona covers. That is the blind spot, and [step 3b](#step-3b-brownfield-a-cluster-that-already-has-apps) closes it.

To manage the ClusterPersona yourself via GitOps instead, install with `--set operator.autoCreateClusterPersona=false` and apply your own.

## Step 3: Give the operator something to watch

The operator only acts on applications that have an `ApplicationPersona`, and it correlates a signal to a persona **by name prefix**, so the persona name must be a prefix of the pod names.

```bash
dorgu persona apply ./my-app -n demo
```

Or apply one directly:

```yaml
apiVersion: dorgu.io/v1
kind: ApplicationPersona
metadata:
  name: nginx
  namespace: demo
spec:
  name: nginx
  type: web
  tier: standard
  resources:
    requests:
      cpu: 50m
      memory: 64Mi
    limits:
      cpu: 500m
      memory: 128Mi
  scaling:
    minReplicas: 1
    maxReplicas: 5
  health:
    livenessPath: /
    readinessPath: /
    port: 80
  policies:
    security:
      runAsNonRoot: true
```

<Warning>
  Always declare `resources.limits`. Without a current limit the remediation proposer has no baseline to compute a bounded change from, and skips the persona with `persona has no resource limits configured`.
</Warning>

```bash
dorgu persona status nginx -n demo
```

The operator validates the running Deployment against the persona and reports issues in `.status.validation.issues` — missing resource requests, an unenforced `runAsNonRoot`, a missing liveness probe. The phase reflects the overall state (`Active`, `Degraded`, or `Failed`), and it re-validates every 60 seconds or immediately when the Deployment changes. See [validation](/operator/features/validation).

<Note>
  **No label is required on the Deployment.** The operator resolves a persona to its workload through an ordered chain: the `app.kubernetes.io/name` label on the Deployment, then the `app` label, then `metadata.name`, then `spec.selector.matchLabels`. Helm, kustomize, and most hand-written YAML label the pod template only, and that resolves through the last rung. When it cannot resolve, the persona reports `NoDeployment` or `AmbiguousDeployment` and names what it tried: see [troubleshooting](/operator/features/self-healing#troubleshooting).
</Note>

## Step 3b: Brownfield, a cluster that already has apps

Writing a persona by hand is fine for one app. It is not how you onboard a cluster that already runs twenty of them, and until a persona exists the operator sees nothing: no persona means no incident, which means no proposed fix.

`dorgu persona import` reads the live Deployments and synthesizes a persona for each from what is already in the spec: resources, probes, replicas, ports, image, and ownership labels. No local source, no Dockerfile, no relabelling.

```bash
# What is Dorgu not watching?
dorgu health

# Read the personas before anything reaches the cluster.
# Diagnostics go to stderr, so the redirect is safe.
dorgu persona import -n apps --all > personas.yaml

# Apply them
kubectl apply -f personas.yaml        # or: dorgu persona import -n apps --all --apply

# Confirm each one resolved to its Deployment
dorgu persona list -n apps
```

<Warning>
  Pay attention to the inferred-limits warning. Where a container declares no resource limits, import derives them and says which ones it invented. The remediation proposer skips any persona without limits, so a persona with limits nobody chose will heal against the wrong numbers. Review them before you rely on them.
</Warning>

The full walkthrough, including breaking an imported app and healing it, is in the [CLI quickstart](/cli/quickstart#brownfield-a-cluster-that-already-has-apps). Requires CLI v0.9.0 or newer.

## Step 4: Break something and watch the loop

The fastest way to see self-healing work is a deliberate OOM. The [CLI quickstart](/cli/quickstart#3-deploy-an-app-that-will-break) has a ready-to-apply manifest: a container that allocates ~90 MB against a 64Mi limit, plus a matching persona.

Once it is crash-looping, one detection cycle later:

```bash
dorgu incidents list -n demo                       # OOMKilled + CrashLoopBackOff
dorgu incidents describe <incident-name> -n demo    # root cause, confidence, provider
dorgu remediation list -n demo                      # one proposal, PLAN: ai-anthropic
dorgu remediation diff <remediation-name> -n demo   # the ordered plan, with diffs
```

## Step 5: Approve, and watch it heal

```bash
dorgu remediation approve <remediation-name> -n demo
```

The operator patches the `ApplicationPersona` spec — the app's desired state — and moves the remediation to `Applying`. The CLI then patches the Deployment with your credentials so the pod actually recovers.

```bash
kubectl -n demo get pods
```

<Note>
  The remediation stays in `Applying` / `Verifying` for the verification window — 10 minutes by default — before it reports `Completed`. At the end of that window the operator re-runs detection and rolls the change back automatically if health regressed. Your pod is healthy well before then.
</Note>

<Warning>
  The operator never creates or modifies Deployments, Services, or any other workload resource. It updates Persona, Incident, and Remediation CRDs and recommends; applying workload changes stays with the CLI, ArgoCD, Flux, or `kubectl`.
</Warning>
