title: "Dorgu Operator"
description: "Kubernetes operator for cluster-side validation, discovery, and persona lifecycle management"
---

The Dorgu Operator is the AI SRE that runs inside your cluster. It detects incidents, diagnoses their root cause, and proposes reviewable fixes. It also validates deployments against persona constraints and discovers cluster state. It is the cluster-side companion to the [Dorgu CLI](/cli/quickstart).

## What the operator does

<CardGroup cols={2}>
  <Card title="AI self-healing" icon="heart-pulse" href="/operator/features/self-healing">
    Detects OOMKills, crash loops, saturation, and node pressure; diagnoses root cause; proposes an ordered fix with guardrails and automatic rollback. Human approval required by default.
  </Card>
  <Card title="ApplicationPersona validation" icon="shield-check">
    Validates deployments against persona constraints: resource limits, replica counts, health probes, and security context. Issues are reported in the persona's status.
  </Card>
  <Card title="ClusterPersona discovery" icon="radar">
    Discovers cluster state including nodes, add-ons, resource capacity, Kubernetes version, and platform type. Reconciles every 5 minutes.
  </Card>
  <Card title="ArgoCD integration" icon="arrows-rotate">
    Watches ArgoCD Application resources and reflects sync status, health status, and revision info into the persona's `.status.argoCD` field.
  </Card>
  <Card title="Prometheus baselines" icon="chart-line">
    Queries Prometheus for CPU and memory usage over a 1-hour window and stores baselines in `.status.learned.resourceBaseline`.
  </Card>
</CardGroup>

<Note>
  **Non-invasive design** -- The operator never creates or modifies workload resources (Deployments, Services). It reads cluster state, updates its own CRDs, and recommends. When you approve a remediation it patches the ApplicationPersona spec — the app's desired-state record — and the CLI applies the workload change with your credentials. This is a core architectural invariant, not a setting.
</Note>

## How it works

```mermaid
flowchart LR
    Op["Operator"] -->|reads state| K8s["Cluster Resources"]
    Op -->|writes incidents and proposals| CRD["Dorgu CRDs"]
    CRD -->|reads proposals| CLI["Dorgu CLI"]
    CLI -->|writes approval| CRD
    CLI -->|patches with your credentials| K8s
```

The operator observes and proposes; the CLI is how a person reads a proposal, approves or rejects it, and applies the workload change. You, `dorgu persona import`, or your GitOps pipeline own the `spec` fields of an `ApplicationPersona` (desired state), and the operator owns the `status` fields (observed reality). The one exception is an approved remediation, where the operator patches the persona's `spec` to the value you approved.
