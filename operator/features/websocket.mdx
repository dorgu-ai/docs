---
title: "WebSocket Server"
description: "An optional event stream the operator can serve. No Dorgu command uses it."
---

The operator can run an optional WebSocket server that pushes persona and cluster state changes to connected clients. It is **off by default**, and since CLI `v0.13.0` **no Dorgu command connects to it**. The `dorgu watch` and `dorgu sync` commands and `dorgu health --watch`, which were its only clients, were removed in that release.

<Note>
  **You do not need it for anything Dorgu does.** Detection, diagnosis, proposals, approval, and healing all work through the Kubernetes API and the Dorgu CRDs. To follow changes live, watch the CRDs directly:

  ```bash
  kubectl get incidentmemories -A -w
  kubectl get remediationactions -A -w
  kubectl get applicationpersonas -A -w
  ```
</Note>

## Configuration

| Helm value | Flag | Default | Description |
|------------|------|---------|-------------|
| `websocket.enabled` | `--enable-websocket` | `false` | Start the server |
| `websocket.port` | `--websocket-addr` | `9090` (`:9090`) | Listen port |
| `websocket.service.type` | | `ClusterIP` | Service type for the endpoint |
| `websocket.service.port` | | `9090` | Service port |

When enabled, the server exposes `/ws` for the WebSocket upgrade and `/health` for liveness, and the chart creates a Service for it. Keep that Service internal to the cluster.

<Warning>
  **The message protocol is not a stable interface.** It is undocumented on purpose, and topics and message shapes may change or be removed in any release. If you build a client on it, pin the operator version and expect to revisit it on upgrade. The CRDs, read through the Kubernetes API, are the supported way to observe Dorgu.
</Warning>
