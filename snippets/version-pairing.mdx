<Note>
  **Current versions: CLI `v0.14.1` with operator `v0.13.1`** (Helm chart `0.13.1`; the chart version, the chart `appVersion`, and the operator version are always the same number). Newest of each is always the right answer, and this note is the only place in these docs that states which that is.

  **CLI `v0.13.0` removed the manifest generation and cluster setup commands** (`generate`, `init`, `config`, `persona generate|apply`, `cluster setup|info|init`, `platform serve`, `watch`, `sync`), so if you relied on one, read the [CLI migration guide](https://github.com/dorgu-ai/dorgu/blob/master/MIGRATION.md) before upgrading.

  **On arm64 nodes, `0.11.1` is a floor and not a preference.** Every operator image published before it, up to and including `0.11.0`, was pushed as a single-platform `amd64` manifest rather than a manifest list. That covers AWS Graviton nodegroups and any kind or k3d cluster on an Apple Silicon Mac. On containerd there is no manifest list to select from, so the pull **succeeds** and the container dies immediately with `exec /manager: exec format error` and exit code 255. The pod reads `CrashLoopBackOff`, not `ImagePullBackOff`. `0.11.1` is that image and nothing else: no API, CRD, controller, or chart-template change, which is why everything below still names `v0.11.0` as the release each behaviour landed in.

  **CLI `v0.14.0` and operator `v0.13.0` are a pair, and the order you upgrade them in matters.** `v0.13.0` adds the approval-time re-check and the apply ticket. A CLI older than `v0.14.0` does not read tickets, so it patches the Deployment from the plan with none of those checks, and the operator cannot stop it. **Upgrade the CLI first, then the operator.** Steps, breaking changes and new settings are in the [upgrade guide](/upgrade-guide).

**CLI `v0.14.1` and operator `v0.13.1` are the patch release of that pair.** They change no CRD, no RBAC and no flag or Helm value, and they are meant to move together: upgrade the CLI first, as before. `dorgu report` counts a refusal that has since cleared only with CLI `v0.14.1` against operator `v0.13.1`. With an older half it reads the live `ProposalRefused` condition as it always did, and a refusal that cleared before the report ran is not counted. See [the changelog](/changelog).

Before that pair, every field either side had added was optional and additive, so a half that did not know about a field simply saw it absent and nothing had to move in lockstep. The ticket is the exception.

These mismatches change behaviour. Two are unsafe, the first and the last, and in both it is the old **CLI** that is the risk, not the old operator:

  | Mismatch | What happens |
  |----------|--------------|
  | **CLI older than `v0.14.0` against operator `v0.13.0` or newer** | **Upgrade the CLI.** An older CLI reads `spec.steps[]` and patches the Deployment without a ticket, so the approval-time re-check, the ticket checks and the ownership re-detection do not apply to that patch. The operator cannot prevent it. |
| **CLI `v0.14.0` against operator older than `v0.13.0`** | Safe but limited. `approve` records the decision, waits up to 30 seconds, finds no ticket, patches nothing and says why. An older operator still patches the ApplicationPersona when it sees the approval, so the persona changes while the workload does not, and the two disagree until you upgrade the operator or revert the persona by hand. Use `approve --no-heal` only if you will apply the change yourself. |
| **CLI `v0.9.0` or older against operator `v0.9.0` or newer** | **Upgrade the CLI.** An older CLI never reads `spec.workloadRef`, so `approve` will patch a Deployment that Helm, ArgoCD, or Flux owns and break the owner's next apply. The operator supplies the ownership facts; declining the patch is the CLI's job. This is the one combination that silently does the thing the guard exists to prevent. |
  | CLI `v0.10.0` or newer against operator `v0.8.1` or older | Conservative rather than dangerous. The operator writes no `workloadRef`, an absent record is treated as owned, and every remediation carrying a workload change is declined with exit `4`. `dorgu remediation approve <name> -n <ns> --no-heal` records the decision until the operator is upgraded. |
  | CLI `v0.12.0` or newer against operator `v0.10.0` or older | No guardrail verdicts. They are read from the optional [`spec.steps[].safety`](/cli/architecture/crds#step-safety-fields) field that operator `v0.11.0` adds. The field is absent, `remediation list` grows no `GUARDRAIL` column, and every command prints what it printed before. |

  One operator upgrade is worth doing on its own merits, with no CLI implication at all: **with `aiRemediation.enabled=true`, operator `v0.11.0` is the release that made AI-planned remediations appliable.** On `v0.10.0` and older, a plan that diagnosed a resource change could be persisted with nothing to apply. See [AI setup](/operator/configuration/ai-setup).

  Operator `v0.12.0` is worth upgrading to on its own as well: it protects the namespace Dorgu is installed in from remediation, and it makes `healthCheck.enabled=false` mean no incidents and no proposals. It also removed the validating webhook, so **an upgrade that still sets `webhook.enabled=true` fails** until you drop the value. See [Helm values](/operator/configuration/helm-values#removed-the-validating-webhook).

  Operator `v0.13.0` is the release that makes an approval safe to give on a cluster you care about: the gate runs again at approval on the live cluster, and what is applied is a short-lived ticket. It also adds probe and restart detection and a complete set of metrics. It needs the CRDs applied and a `v0.14.0` CLI. See [How Dorgu decides](/how-dorgu-decides).

Operator `v0.12.1` is the one to install if you turn on AI: it keeps incidents in protected namespaces, including the namespace Dorgu runs in, out of every model call. On `v0.12.0` the diagnosis call still sent them. No values, flags or RBAC change.

  Both mismatch directions in full, with the ownership reasoning behind them: [version coupling](/ownership-model#version-coupling). Newest published releases: [CLI](https://github.com/dorgu-ai/dorgu/releases) and [operator](https://github.com/dorgu-ai/dorgu-operator/releases).
</Note>
