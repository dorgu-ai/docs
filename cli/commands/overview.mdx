## Command tree

```
dorgu
├── health                  Show cluster health summary
├── incidents               View detected incidents
│   ├── list                List incidents
│   └── describe <name>     Show incident details
├── remediation             Review and act on proposed fixes
│   ├── list                List remediation proposals
│   ├── diff <name>         Show the proposed change
│   ├── approve <name>      Approve a pending remediation and heal the workload
│   ├── reject <name>       Reject a remediation proposal
│   └── heal <name>         Apply an approved remediation to the workload
├── persona                 ApplicationPersona CRDs
│   ├── import              Create personas from Deployments already running
│   ├── list                List personas across namespaces
│   └── status <name>       Check persona status
├── cluster                 ClusterPersona CRDs
│   └── status [name]       View cluster status
├── version                 Show version info
└── completion              Generate a shell completion script
```

<Note>
  `dorgu incidents` has only `list` and `describe`. There is no `history` subcommand.
</Note>

<Info>
  **CLI `v0.13.0` removed every command that was not part of the self-healing loop:** `generate`, `init`, `config`, `persona generate`, `persona apply`, `cluster init`, `cluster setup`, `cluster info`, `platform serve`, `watch`, `sync`, `health --watch`, and the global `--config` flag. The [CLI migration guide](https://github.com/dorgu-ai/dorgu/blob/master/MIGRATION.md) lists what to use instead for each one.
</Info>

## Command reference

The command tree above is a plain listing. Use these links for the full flag reference on each command group.

| Command | Reference | What it does |
|---------|-----------|--------------|
| `dorgu health` | [health](/cli/commands/health) | Cluster health summary |
| `dorgu incidents` | [incidents](/cli/commands/incidents) | List and inspect detected incidents |
| `dorgu remediation` | [remediation](/cli/commands/remediation) | Review, approve, reject, and apply proposed fixes |
| `dorgu persona` | [persona](/cli/commands/persona) | Import and inspect ApplicationPersona CRDs |
| `dorgu cluster` | [cluster](/cli/commands/cluster) | Inspect the ClusterPersona the operator maintains |
| `dorgu version` | [version](/cli/commands/version) | Show version info |
| `dorgu completion` | `dorgu completion --help` | Shell completion for bash, zsh, fish, and PowerShell |

## Global flags

These flags apply to all commands:

| Flag | Description | Default |
|------|-------------|---------|
| `--context` | kube-context for every `kubectl` call the command makes | the kubeconfig's current-context |
| `--json` | Output as JSON | `false` |
| `--no-color` | Disable colored output | `false` |

Cluster commands also take `--kubeconfig`. Both it and `--context` are applied to every `kubectl` call a command makes, so a command never reads one cluster and writes another. `heal`'s [production-context guard](/cli/commands/remediation#protected-contexts) checks the `--context` value when you set it, and the kubeconfig's current-context otherwise.

## Prerequisites

Every command that touches a cluster shells out to **`kubectl`**, so it must be on your `PATH`, and either your current context or `--context` must point at the target cluster. Without it those commands fail with `kubectl not found in PATH`. Only `version` and `completion` work with no cluster at all.

Set `DORGU_DEBUG=1` to see `kubectl`'s raw output in error messages. By default the CLI strips klog noise (the `memcache.go:265 "Unhandled Error"` lines) so the message that says what went wrong is not buried.

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Success |
| `1` | Error: the command could not run. An unreachable cluster, a missing kubeconfig, no `kubectl`, a failed API call. |
| `2` | `dorgu health --exit-code` only: active critical incidents |
| `3` | `dorgu health --exit-code` only: health could not be judged |
| `4` | `dorgu remediation approve` / `heal` only: **declined by design.** Dorgu understood the plan and chose not to write, because something else owns the workload. Nothing failed and nothing changed. |

Codes 2 and 3 are opt-in and specific to [`dorgu health`](/cli/commands/health#exit-codes). An unknown subcommand is an error with a non-zero exit, not a help dump.

<Warning>
  **`4` is a decision, not a failure.** A wrapper that treats every non-zero exit as breakage will report a successful refusal as an error. Accept `4`, or use [`--no-heal`](/cli/commands/remediation#recording-a-decision-without-a-patch), which records the decision without a workload patch and exits `0`. See [the ownership model](/ownership-model#exit-code-4-declined-by-design).
</Warning>
