---
title: dorgu report
description: Print a local summary of how the loop is doing on this cluster, as text or as JSON (schema dorgu.report/v1)
---

## Overview

`dorgu report` answers "is this working here?" from the cluster's own records. It reads `RemediationAction`, `IncidentMemory`, persona and Event resources, computes the numbers below for a time window, and prints them. It sends nothing anywhere. If you are a design partner, the output is what you paste to the Dorgu team.

It is read-only and needs **CLI v0.14.0**. The heal and refusal sections need **operator v0.13.0** or newer, which is the release that writes the records they are computed from.

<Note>
  **It never prints a zero for something it could not measure.** A figure with no sample behind it reads `no data` (`null` with `no_data: true` in JSON). A cluster read that fails is named in the output, and every section that depends on it says `no data` with the reason. A zero in this report is a measurement.
</Note>

## Synopsis

```bash
dorgu report [flags]
```

### Flags

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--since` | string | `7d` | Window to report on: `7d`, `24h`, `2w`, `90m`, or any Go duration |
| `-n, --namespace` | string | all namespaces | Limit the report to one namespace |
| `--kubeconfig` | string | `kubectl`'s own resolution: `$KUBECONFIG`, then `~/.kube/config` | Path to the kubeconfig |
| `--json` | bool | `false` | Print JSON, schema `dorgu.report/v1` (inherited global flag) |

### Examples

```bash
dorgu report
dorgu report --since 24h
dorgu report --since 30d --json
dorgu report -n production
```

## What it reports

| Section | What it tells you |
|---------|-------------------|
| **North star: safe heals** | Clean heals whose approval-time gate run passed. A heal is **clean** only when the RemediationAction completed, `HealCredited` is `True`, and the incident outcome is `resolved`. |
| **Heal accounting** | How every RemediationAction created in the window ended, and why each one that is not a clean heal is not one: `partial`, `self_resolved`, `heal_not_credited`, `no_credit_record`, `outcome_unconfirmed`, `rolled_back`, `approved_not_healed`, `failed`, `rejected`, `expired`, `acknowledged`, `refused_by_gate`, `in_flight`. Every action lands in exactly one bucket. `approved_not_healed` is an approval that never became a heal: it was approved with `--no-heal` (or never patched), so the workload kept its problem and the operator rolled the persona back. It is not counted as a rollback of a heal. |
| **Active cluster, review depth, approval rate** | Whether any proposal was decided in the window, decisions per week, and approved against rejected. Below 5 decisions it prints the counts and says `too few decisions` instead of a rate. Beyond that, an approval rate under 30% reads as noisy proposals and over 80% as possible rubber-stamping. |
| **Time to heal** | p50 and p90 for detect to proposal, proposal to decision (human time), decision to applied, and applied to verified. Detect to proposal is measured once per incident, to its first proposal. |
| **Proposal precision** | The share of decided proposals rejected with the reason `wrong-diagnosis`, and a breakdown of every other reason. See [`remediation reject`](/cli/commands/remediation#remediation-reject). |
| **Refusal mix** | What the gate refused, by phase (proposal, approval, apply), stage and reason, with each reason's share of proposals. A reason over 30% of proposals, on at least 10 proposals, is flagged. An outstanding proposal is shown separately as `deferred`, because it is waiting for a decision and is not a refusal. |
| **First-run clamps** | How many proposals had a value narrowed by a guardrail before you saw the plan, by guardrail. |
| **CLI declines** | Times `approve` or `heal` declined, by reason. Kubernetes keeps Events for about an hour, so declines older than that are not counted. |
| **Not measurable from a cluster** | The measures a cluster cannot report (external installs, design partners, time to first value, retention, and similar), listed so their absence is not read as zero. |

The text output labels some lines with short IDs (`A2`, `A5`, `A6`, `Q1`, `Q2`, `Q3`, `Q6`). They name the measure, so two pasted reports can be compared line by line.

The example shortens the long text fields and lists only two of the `not_measurable` entries. These are the top-level fields and what they hold:

| Field | Holds |
|-------|-------|
| `schema`, `generated_at`, `window` | The schema name, when the report ran, and the window as `since`, `start` and `end` |
| `cluster` | Context only: no number is computed from it. `application_personas` is `null`, never `0`, when the personas could not be read, and `self_healing_modes` is `null` or empty when the ClusterPersonas could not be read |
| `sources` | For each of `remediation_actions`, `incidents`, `personas`, `cluster_personas` and `events`: `ok`, `count`, and an `error` class when a read failed |
| `input_errors` | One `{input, error}` entry per failed read. `error` is one of `forbidden`, `not_found`, `timeout`, `unparseable`, `error` |
| `heal_accounting` | `total`, `completed`, `clean` and `safe_heals` (both `null` when they cannot be known), `no_data` with `reason`, `excluded` (a count per bucket, zeros included), and `heal_not_credited_by_reason` |
| `tier_a` | `ns_safe_heals` (`safe_heals`, `clean_heals`, `no_data`, `reason`), `a2_active_cluster` (`active`, `proposals_decided`), `a5_review_depth` (`per_week`, `window_days`), `a6_approval_rate` (`approved`, `rejected`, `rate`, `too_few_decisions`, `band`), `a7_external_agent_share`, `decisions` and `notes` |
| `tier_q` | `q1_time_to_heal` (`detect_to_proposal`, `proposal_to_decision`, `decision_to_applied`, `applied_to_verified`, each `n`, `p50_seconds`, `p90_seconds`, `no_data`), `q2_proposal_precision` (`decided`, `wrong`, `rate`, `rejections_by_reason`), `q3_llm_efficiency` (`plan_sources`), `q6_refusal_mix` (`proposals`, `rows[]` of `phase`, `stage`, `reason`, `count`, `share_of_proposals`, `flagged`, and `deferred_proposals`) |
| `first_run_clamps` | `proposals_with_clamp`, `step_verdicts`, `clamps_by_rule`, `gate_clamps_by_guardrail`, `no_data` |
| `cli_declines` | `by_reason` (event reason to count), `no_data`, and a `note` on the one-hour Event retention |
| `not_measurable` | `{id, name, reason}` entries |

<Warning>
  **Check `no_data` before you read a number.** `clean`, `safe_heals`, a percentile or a rate is `null` when it cannot be known, and `no_data` is `true` with a `reason`. A script that treats `null` as `0` will report a failure to read as a fact.
</Warning>

### The operator line in the header

The header prints the operator version only when the operator's image tag is a release version. A commit hash, `latest` or `dev` reads `Operator:  unreleased build <tag>`, so a build identifier is never shown as if it were a version. `cluster.operator_version` in the JSON keeps the raw tag.

### Older operators

Against an operator older than `v0.13.0`, which writes no tickets and no `HealCredited` record, the heal sections are `no data` with the operator version in the reason. The same is true when the operator version cannot be determined (for example an image pinned by digest, or a tag such as `latest`) and the window has completed actions with no `HealCredited` record. The report fails toward `no data`, not toward a measured zero.

### Permissions

The report reads, with the identity in your kubeconfig, `remediationactions`, `incidentmemories`, `applicationpersonas`, `clusterpersonas`, Events about RemediationActions, and Deployments (to read the operator's version). If a read is forbidden, it is listed in `input_errors` and the sections that depend on it say `no data`. The command needs `kubectl` on your `PATH`, like every `dorgu` command that talks to the cluster.
