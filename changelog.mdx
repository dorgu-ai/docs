This page covers the releases that change how you use Dorgu. The full history, release by release, is in each repository's changelog: [CLI](https://github.com/dorgu-ai/dorgu/blob/master/CHANGELOG.md) and [operator](https://github.com/dorgu-ai/dorgu-operator/blob/master/CHANGELOG.md).

<Update label="CLI v0.14.1 · operator v0.13.1" description="2026-11-09: stale proposals expire, owned workloads get advice only, and the report stops losing refusals">
  A patch release for what the first upgrade to `v0.13.0` turned up. No CRD change, no RBAC change, and no new command, flag or Helm value. **Upgrade the CLI first,** as before. The upgrade steps are in the [upgrade guide](/upgrade-guide#what-the-patch-release-changes).

  ## Upgrade steps

  - **If a tool reads the `Expired` condition's reason,** handle the new `IncidentResolved`. It is terminal and applies nothing.
  - **If a script reads `dorgu report --json`,** accept `null` in `tier_q.q6_refusal_mix.deferred_proposals`. It was `0` before.
  - **If a dashboard reads `dorgu health --json`,** read `pendingRemediations.count` (the `Pending` proposals) and the new `pendingRemediations.approved` together, where you used the old `count` as both.
  - **Do not rely on the registry chart attestation for 0.13.1.** See [verify what you install](/operator/installation#verify-what-you-install-build-provenance).

  ## Operator v0.13.1 and Helm chart 0.13.1

  **Fixed**

  - **A stale `Pending` proposal no longer silences the persona.** A proposal whose incident has resolved expires with the reason `IncidentResolved` at the start of the next cycle, before anything is proposed. In one dogfood run, 25 proposals were deferred behind four stale ones. An expired proposal still counts toward the hourly rate limit, so a recurrence within the hour can be refused by `rate-limit`. Approved proposals are never touched. See [human approval](/how-dorgu-decides#human-approval).
  - **A workload that Helm, Argo CD, Flux or kustomize owns gets advice only.** No step is auto-executable, and the persona change is now a `config-change` step. **Approving one records `Acknowledged` and changes nothing in the cluster.** Operator `v0.13.0` issued a ticket and patched the persona. See [ownership](/how-dorgu-decides#ownership).
  - **A refused step command no longer loses the whole proposal.** Only the advisory steps whose command is not one plain `kubectl` invocation are dropped, and the rest goes through the gate again. Dorgu cuts runs of three or more words of the refused command out of the text it keeps. A paraphrased command is not caught, and a plain `kubectl` command the gate already judged is kept. See [when a printed command is refused](/how-dorgu-decides#when-a-printed-command-is-refused).
  - **A description that reads `placeholder`, `todo`, `tbd` or `n/a`,** or is empty, is filled from the plan summary, and a step that cannot be filled is dropped.
  - **An empty AI plan is an unusable reply.** It is asked once more, counted in `dorgu_llm_invalid_output_total{purpose="planning"}`, and remembered for 5 minutes instead of being cached as a success. See [AI setup](/operator/configuration/ai-setup#how-often-the-model-is-asked-and-what-it-may-return).

  **Added**

  - **`ProposalRefusalRecorded`,** a condition on the IncidentMemory that keeps a refusal after `ProposalRefused` has cleared. See [the CRD reference](/cli/architecture/crds#conditions-and-annotations).
  - **Build provenance attestations** for the operator image, the chart archive and the chart in the registry. See [verify what you install](/operator/installation#verify-what-you-install-build-provenance). Releases before this one have none.
  - New metric label values, at zero: the gate reason `owner-auto-step` and the cache result `unusable`. See the [metrics reference](/operator/reference/metrics).

  **Documented, not changed**

  - **A recurrence or an escalation keeps the name of the incident it continues.** An OOM that recurs on a crash-looping pod is still `...-crashloopbackoff-...-r1`. The name is the lineage, which the gate's dedup and the rejection cooldown depend on. The current signal is in the `Signal` column of `kubectl get incidentmemories` and the `dorgu.io/signal` label.

  ## CLI v0.14.1

  **Fixed**

  - **`dorgu health` says what it counts.** "Awaiting approval" is the `Pending` proposals only, and `Approved, not yet applied: N` is its own line, shown when N is above zero. See [`dorgu health`](/cli/commands/health#output-sections).
  - **`dorgu report` no longer misses refusals that happened.** It counts a refusal from the operator's `ProposalRefusalRecorded` condition, once per incident, even after the incident resolved. It needs operator `v0.13.1`. A refusal an older operator already cleared cannot be recovered. See [the report](/cli/commands/report#refusals-are-counted-after-they-clear).
  - **`dorgu report` no longer prints `0` for deferrals it cannot know.** Text reads `not recorded on cluster objects`, and `deferred_proposals` is `null` with a `deferred_note`. See [deferrals](/cli/commands/report#deferrals-are-not-counted-here).
  - **`approve` explains the `IncidentResolved` expiry:** the incident resolved, the advice is stale, and nothing is wrong with your approval.
  - **A refusal that came back is dated by its latest occurrence,** so one standing now is inside the report's window.

  **Added**

  - **Build provenance attestations** for every release archive and `checksums.txt`. Verify with `gh attestation verify <file> --owner dorgu-ai`. See [verifying build provenance](/cli/installation#verifying-build-provenance). Releases before this one have none.
</Update>

<Update label="CLI v0.14.0 · operator v0.13.0" description="2026-11-09: approval goes through the gate again, and what is applied is a ticket">
  An approval no longer applies anything by itself. The operator re-checks it against the live cluster and issues a short-lived apply ticket, and the CLI applies exactly that ticket. The two halves are a pair: read the [upgrade guide](/upgrade-guide), and **upgrade the CLI first**, because a CLI older than `v0.14.0` ignores tickets and patches from the plan with none of the new checks. The full path is on [How Dorgu decides](/how-dorgu-decides).

  ## Upgrade steps

  - **Upgrade the CLI to `v0.14.0` on every machine and CI job that runs `approve` or `heal`,** then apply the new CRDs, then upgrade the chart to `0.13.0`. Both `--reuse-values` and `--reset-then-reuse-values` work.
  - **If a script calls `dorgu remediation reject --reason "some text"`,** change it. `--reason` is now one of `wrong-diagnosis`, `too-risky`, `not-now`, `duplicate`, `not-needed`, `other`, and free text goes in `--note`. **This is breaking.**
  - **If you set `websocket.*` Helm values or pass `--enable-websocket`,** remove them. The server is gone. The flags stop the operator at startup, and old values are ignored.
  - **If you manage the operator's ClusterRole yourself,** add `delete` on `incidentmemories.dorgu.io`.
  - **Decide your `Pending` proposals before you upgrade, or let them go.** One created by an older operator cannot be approved afterwards. It ends `Expired` with the reason `PredatesGate`, and the operator proposes again.

  ## Operator v0.13.0 and Helm chart 0.13.0

  **Added**

  - **An approval-time re-check and an apply ticket.** On approval the gate runs again on the live cluster and either writes `status.applyTicket` (phase `Ticketed`, valid 10 minutes) or refuses with the reason on a `GateRefused` condition. The ticket is the only thing applied. See [the re-check](/how-dorgu-decides#the-approval-time-re-check-and-the-apply-ticket).
  - **One gate with six stages,** Validate, Ground, Ownership, Guardrails, Mode policy and Dedup and cooldown, for every proposal. Facts and verdicts are recorded on `status.gate`.
  - **Every refusal is recorded three ways:** a condition, a Kubernetes Event (`Dorgu<Stage>Refused`) and a metric. An outstanding proposal is a deferral, not a refusal. See [refusals are recorded](/how-dorgu-decides#refusals-are-recorded).
  - **Heal credit.** A recovery is credited to Dorgu only when the CLI patched the workload and the live values equal the ticket's. Otherwise the incident is `self-resolved` or the heal is `partial`. See [heal credit](/how-dorgu-decides#heal-credit).
  - **New signals `ReadinessNotReady`, `LivenessRestarts` and `RestartLoop`,** which catch probe failures and restart loops that raised nothing before. See [Detect](/operator/features/self-healing#probe-failures-and-restart-loops).
  - **Recurrence, escalation and pruning.** A fault that returns opens a new incident (`-r<N>`), one that changes shape is one escalating incident, a flapping fault is capped, and old resolved incidents are pruned. See [recurrence, escalation and pruning](/how-dorgu-decides#recurrence-escalation-and-pruning).
  - **Pending proposals expire after 24 hours** (`remediation.pendingTTL`). The `Expired` reason is `ApprovalTimedOut`, `Superseded`, or `PredatesGate`.
  - **A complete [metrics reference](/operator/reference/metrics):** gate decisions, stage durations, tickets, heal credit, verifications, rollbacks and model use, all pre-registered at zero.
  - New flags and values: `healthCheck.readinessThreshold`, `healthCheck.livenessRestarts.count` and `.window`, `healthCheck.recurrence.cap` and `.window`, `healthCheck.resolvedRetention`, `remediation.pendingTTL`, `llm.cacheTTL`, `eventPipeline.enabled`.

  **Changed**

  - **`spec.action` is deprecated.** It is a notification only. `spec.steps[]` is the only plan.
  - **The AI is asked once per changed situation,** and its replies must be strict JSON. The rules choose the action and the deduplication key, and the model's `recommendedAction` is never acted on.
  - **Pod detection skips the namespaces the gate refuses,** including `safety.excludedNamespaces` and the ClusterPersona's `excludeNamespaces`. A pod failing there raises no incident.
  - **One OOM is one incident.** A stale `OOMKilled` is no longer a live signal.
  - **Rollback never overwrites a later edit.** A rollback that restored the persona but not the live Deployment is `partial`.
  - **Verification fails closed.** If any collector failed, the result is `Unknown`, never `Healthy`, and an `Unknown` result is retried and then rolled back.
  - **More paths fail closed:** an unreadable rate limit, an unreadable self-healing mode, an unknown operator namespace.
  - **The ClusterRole gains `delete` on `incidentmemories.dorgu.io`,** and nothing else.
  - **Advisory proposals survive a refused AI plan.** For a crash loop, a not-Ready container or a liveness kill, the planner's persona change is dropped and its advisory steps are proposed, with the refusal still recorded.
  - **One bad image is one incident.** `PodPendingLong` is no longer raised for a pod stuck on an image pull error.
  - **A container that exits right after it starts is detected in about a minute.**
  - **The leader lease is released on shutdown,** so a rolling update no longer leaves detection without a leader for about 30 seconds.
  - **Rollback is stated plainly.** It restores the persona only. When the workload still carries the change the outcome is `partial` and the condition carries the command that finishes the job. If the workload was never patched, `WorkloadDiverged` is `False/WorkloadRestored`.

  **Removed**

  - **The WebSocket server,** its `--enable-websocket` and `--websocket-addr` flags and the `websocket.*` chart values. It was unauthenticated and nothing used it.
  - **The event pipeline is off by default.** Turn it on with `eventPipeline.enabled=true`. `dorguEvents.*` values you set do nothing until you do.

  ## CLI v0.14.0

  **Added**

  - [**`dorgu report`**](/cli/commands/report): a local summary of safe heals, approvals, time to heal, refusals and clamps, as text or JSON (schema `dorgu.report/v1`). It never prints a zero for something it could not measure.
  - **`remediation reject --reason` and `--note`.** The reason is recorded as a `RejectionReason` condition and counted by `dorgu report`.
  - **Every decline is recorded as an Event** on the RemediationAction. A protected kube context writes nothing to the cluster.
  - **`remediation list` shows `Ticketed` actions by default,** and `dorgu health` prints `Awaiting approval: N` where it used to print `Pending Remediations: N`.
  - **`dorgu report` counts an approval that was never healed as `approved_not_healed`,** not as a rollback, and its header reads `unreleased build <tag>` when the operator's image tag is not a release version.

  **Changed**

  - **`approve` waits up to 30 seconds for the apply ticket and patches exactly the ticket,** after re-reading the action, the Deployment and the cluster's self-healing mode. It refuses without a ticket, with an expired one, or on a changed Deployment. A refusal by the operator's gate exits `4`.
  - **`approve` reports "approved" only if the approval stands.** If the operator expired or superseded the action in the moment between the CLI reading it and writing the approval, the CLI says why (`Superseded`, `ApprovalTimedOut` or `PredatesGate`) and exits non-zero. If the spec changed since you read the plan, it refuses and asks you to re-run `diff`. If someone else's approval landed first, it says `already approved by another actor` and exits `0` without healing.
  - **`heal` no longer doubles as an approval.** Approve first. After `approve --no-heal`, `heal` works only while the action is still `Applying`.
  - **Ownership is re-detected from the live Deployment before every patch.**
  - **`reject --reason` takes a fixed list.** Breaking.

  **Fixed**

  - `remediation diff` suggests a `reject` command that works: `--reason <wrong-diagnosis|too-risky|not-now|duplicate|not-needed|other> [--note "..."]`.
  - `--kubeconfig` help is accurate: with no flag, `kubectl` resolves the config itself and `$KUBECONFIG` wins.
  - AI-written text in `incidents describe` and `remediation diff` is rendered as plain text instead of raw markdown.
  - A protected-context refusal opens with the command you ran: `refusing to approve`, `refusing to approve and heal`, or `refusing to heal`.
  - `remediation diff` on an advisory plan no longer shows a rollback block or says Dorgu may patch the workload.
  - Incidents on workloads with no persona show `(no persona)` in `incidents list` and `health`, and `health --json` gains `attribution`.

  ## Known gaps

  Anyone who can write `remediationactions/status` can forge an approval and a ticket, so treat that permission as the right to approve. Approver identity is not enforced. Two annotations can release a rejection cooldown early. CPU throttling is not detected. Details and the planned fixes are in [the upgrade guide](/upgrade-guide#known-gaps-at-this-release).
</Update>

<Update label="Operator v0.12.1" description="2026-11-07: protected namespaces are kept out of every model call">
  A patch release for operator and chart `0.12.1`. No values, flags or RBAC change, and there are no upgrade steps beyond `helm upgrade`.

  **Fixed**

  - **Incidents in a protected namespace are no longer sent to a model, by the diagnosis call or by the planner.** In 0.12.0 the deny-list stopped the AI planner for a protected persona, but the AI diagnosis call still sent the incident's summary, severity and signal strings (for example `Pod/dorgu-system/<name>`) to your provider every cycle, and recorded the incident as `provider: ai-enhanced`. The planner also had a gap: a node-pressure or eviction diagnosis can name pods from many namespaces under one persona, so a diagnosis for an allowed persona could still mention a protected pod.
  - Now a diagnosis that touches any protected namespace is withheld from the model whole. The incident is still detected, diagnosed by the rules, and recorded, as `provider: rule-based`. Where the planner is withheld, Dorgu falls back to the rule-based proposal, which never calls a model. Namespaces that are not protected behave as before.
  - The planner prompt no longer lists the ClusterPersona `excludeNamespaces`, so the names of namespaces meant to be invisible to the model are no longer sent with each plan request.

  **Changed**

  - **The deny-list fails closed.** If the ClusterPersona deny-list cannot be read, or a resource carries no namespace, the diagnosis is withheld from the model and no AI plan is proposed until the read recovers. The read error is logged at error level. Remediations already in flight are not affected.

  Upgrade with `helm upgrade dorgu-operator oci://ghcr.io/dorgu-ai/dorgu-operator-charts/dorgu-operator --version 0.12.1 -n dorgu-system`. The CLI is unchanged: v0.13.0 was the current release at the time.
</Update>

<Update label="CLI v0.13.0 · operator v0.12.0" description="2026-11-06: Dorgu is the self-healing loop and nothing else">
  Both halves drop every surface that was not part of detect, diagnose, propose, approve, heal. Both releases are breaking if you used one of the removed surfaces, so read the upgrade steps before you upgrade.

  ## Upgrade steps

  - **If you used `dorgu generate`, `init`, `config`, `persona generate|apply`, `cluster setup|info|init`, `platform serve`, `watch` or `sync`,** read the [CLI migration guide](https://github.com/dorgu-ai/dorgu/blob/master/MIGRATION.md). It lists what to use instead for each one. The last commit with them is tagged `pre-harness`.
  - **If your Helm values set `webhook.enabled=true`,** remove it before upgrading the chart. The install fails with a message saying the webhook was removed, rather than silently dropping the value.
  - **If you run the operator binary directly with a `--webhook-*` or `--enable-webhook` flag,** remove the flag. The binary no longer starts with it.

  ## CLI v0.13.0

  **Removed**

  - `generate`, `init`, `config`, `persona generate`, `persona apply`, `cluster init`, `cluster setup`, `cluster info`, `platform serve`, `watch`, `sync`, `health --watch`, `health --operator-url`, and the global `--config` flag. `.dorgu.yaml` and `~/.config/dorgu/config.yaml` are no longer read.
  - The CLI's own LLM integration (OpenAI, Anthropic, Gemini, Ollama). The CLI now makes no calls to a model provider and reads no API key. AI diagnosis and AI plans come from the operator, in your cluster, only when you [enable them](/operator/configuration/ai-setup).

  **Added**

  - A global [`--context`](/cli/commands/overview#global-flags) flag, applied to every `kubectl` call. `persona status`, `persona list` and `cluster status` gain `--kubeconfig`, and every command now honours both on every call it makes. The production-context guard on `approve` and `heal` checks the `--context` value when you set one.
  - [`DORGU_PROTECTED_CONTEXTS`](/cli/commands/remediation#protected-contexts): comma-separated, case-insensitive substrings of kube-context names that `approve` and `heal` refuse to patch a workload through. The default stays `prod`, and a blank value falls back to it.

  **Changed**

  - "Operator not installed" hints now print the `helm install` command for the operator instead of the removed `dorgu cluster setup`.

  **Fixed**

  - A `kubectl` flag value equal to a verb name, as in `kubectl -n logs delete deployment/foo`, no longer makes a write look read-only. On a workload Dorgu does not own, a step command is printed only if it reads, and the verb is now found by position rather than by scanning for the first word that looks like one.
  - `kubectl auth reconcile` and `kubectl rollout -n status restart` are no longer classified as read-only. `auth` and `rollout` are judged by the subcommand that immediately follows them.
  - [Protected contexts](/cli/commands/remediation#protected-contexts) now refuse every `approve`, including `--no-heal`. Approving is itself a change, and the refusal used to suggest `--no-heal` as the way through.

  ## Operator v0.12.0 and Helm chart 0.12.0

  **Removed**

  - The Deployment validating admission webhook, with its `webhook.*` chart values, Service, `ValidatingWebhookConfiguration`, and `--enable-webhook` and `--webhook-*` flags. It never produced a warning or a denial in any release. Persona validation still runs and reports on the persona's status. See [Helm values](/operator/configuration/helm-values#removed-the-validating-webhook).
  - An older code path that opened `OOMKilled` incidents and proposed fixes even with detection turned off.

  **Changed**

  - **`healthCheck.enabled=false` now means what it says.** The operator records persona health only, and never opens an incident or proposes a fix.
  - **`--enable-health-check` defaults to `true` in the binary,** matching the chart, which has defaulted `healthCheck.enabled` to `true` since 0.8.0.
  - **The remediation deny-list protects the namespace Dorgu runs in.** It used to protect a hardcoded `dorgu-operator-system`, so the documented `dorgu-system` install was not covered. The operator now reads its namespace from `POD_NAMESPACE`, which the chart sets. `kube-system` stays protected.

  **Added**

  - [`safety.excludedNamespaces`](/operator/configuration/helm-values#remediation-safety) (flag `--safety-excluded-namespaces`): more namespaces Dorgu never proposes a remediation in. The ClusterPersona's `excludeNamespaces` still applies alongside it.
  - The chart creates a metrics Service and a `metrics-reader` ClusterRole, and exports `dorgu_incidents_total`, `dorgu_proposals_total` and `dorgu_remediation_transitions_total`. See [Metrics and probes](/operator/configuration/helm-values#metrics-and-probes).

  **Fixed**

  - Gemini: the API key is sent in a request header rather than in the URL, and the chart injects the environment variable that matches the chosen `llm.provider`. See [Using Gemini](/operator/configuration/ai-setup#using-gemini).
  - Scraping `/metrics` on a Helm install no longer fails with a 500. With secure metrics on, the chart now grants the operator what it needs to authenticate scrapers.
  - A protected namespace is refused before the AI planner is asked for a plan. The diagnosis call was not covered yet; operator v0.12.1, above, closes that.
</Update>
